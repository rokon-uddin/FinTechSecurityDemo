URLSession Architecture & Configuration

Medium

URLSession is Apple's networking stack — the single API you use for all HTTP/HTTPS communication on iOS. But it is far more than a simple HTTP client. It manages connection pooling, caches, cookies, credentials, authentication challenges, background transfers, and the entire TLS lifecycle. For a payment app like FinTech, every architectural decision you make around URLSession has direct security consequences.

The Three Configuration Types

Every URLSession is initialized with a URLSessionConfiguration. This configuration is copied at creation time — you cannot mutate it after the session is created. Choose wrong here, and sensitive data leaks to disk.

Configuration Comparison
ConfigurationDisk CacheCookiesCredentialsUse Case
.default ✓ Persisted ✓ Persisted ✓ Persisted General-purpose APIs where caching is acceptable
.ephemeral ✗ Memory only ✗ Memory only ✗ Memory only Payment & auth endpoints — always use this
.background(id) ✓ Persisted ✓ Persisted ✓ Persisted Large uploads (KYC docs) that survive app kill
🚫
Critical Security Issue Using URLSession.shared or .default configuration for financial API calls risks writing response data to the on-disk URL cache. That cache survives app restarts and can be read by forensic tools on non-encrypted devices. Always use .ephemeral for any request carrying financial data.
Swift — Production URLSession Setup for Payment APIs
// NetworkSession.swift — singleton network session for FinTech
import Foundation

final class NetworkSession {

    static let shared = NetworkSession()

    let paymentSession: URLSession   // Ephemeral — for all transactional API
    let uploadSession: URLSession    // Background — for KYC document uploads

    private init() {
        // ── Payment session: ephemeral, no caching, custom headers ──
        let payConfig = URLSessionConfiguration.ephemeral

        // Hard disable caching even though ephemeral already does this
        payConfig.requestCachePolicy = .reloadIgnoringLocalAndRemoteCacheData
        payConfig.urlCache = nil

        // Network timeouts — fail fast for payment UX
        payConfig.timeoutIntervalForRequest  = 30   // per-request
        payConfig.timeoutIntervalForResource = 60   // total resource

        // Disable cookies for API session — we manage auth via headers
        payConfig.httpCookieAcceptPolicy  = .never
        payConfig.httpShouldSetCookies    = false
        payConfig.httpCookieStorage       = nil

        // Restrict to cellular + WiFi (allow roaming for BD users)
        payConfig.allowsCellularAccess = true

        // Security headers sent with every request
        payConfig.httpAdditionalHeaders = [
            "Accept":          "application/json",
            "Content-Type":    "application/json",
            "X-Platform":     "iOS",
            "X-App-Version":  Bundle.main.appVersion,
            "X-Build-Number": Bundle.main.buildNumber,
            "X-Request-ID":   UUID().uuidString  // idempotency key
        ]

        // Must use custom delegate — URLSession.shared can't do pinning!
        self.paymentSession = URLSession(
            configuration: payConfig,
            delegate: PinningDelegate(),   // certificate pinning
            delegateQueue: nil             // nil = internal serial queue
        )

        // ── Background session for document uploads ──
        let bgConfig = URLSessionConfiguration
            .background(withIdentifier: "com.fintech.kyc-upload")
        bgConfig.isDiscretionary = false        // upload ASAP, not when convenient
        bgConfig.sessionSendsLaunchEvents = true // wake app when done

        self.uploadSession = URLSession(
            configuration: bgConfig,
            delegate: UploadDelegate(),
            delegateQueue: nil
        )
    }
}

// Convenience extensions for Bundle info
extension Bundle {

        infoDictionary?["CFBundleShortVersionString"] as? String ?? "0.0"
    }
    var buildNumber: String {
        infoDictionary?["CFBundleVersion"] as? String ?? "0"
    }

URLSession Delegate Chain — How Authentication Challenges Work

Understanding the delegate chain is critical for certificate pinning. When a TLS handshake occurs, URLSession fires authentication challenge delegates at two levels:

1
Server Sends Certificate

During TLS handshake, the server presents its certificate chain. URLSession's internal Security framework evaluates it against the system trust store.

2
Task-Level Challenge: urlSession(_:task:didReceive:completionHandler:)

Fires first if implemented. Specific to one URLSessionTask. Override this for per-task behaviour (e.g., different pin for different endpoints).

3
Session-Level Challenge: urlSession(_:didReceive:completionHandler:)

Fires if task-level returns .performDefaultHandling, or if task-level is not implemented. This is where you implement session-wide pinning.

4
Completion Handler Decision

You call the completion handler with: .useCredential (accept), .cancelAuthenticationChallenge (reject & abort), or .performDefaultHandling (defer to system).

Swift — Authentication Challenge Delegate (Full)
final class PinningDelegate: NSObject, URLSessionDelegate {

    // Session-level — catches ALL challenges for this session
    func urlSession(
        _ session: URLSession,
        didReceive challenge: URLAuthenticationChallenge,
        completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void
    ) {
        let method = challenge.protectionSpace.authenticationMethod

        switch method {
        case NSURLAuthenticationMethodServerTrust:
            // ← This is the TLS certificate challenge
            handleServerTrust(challenge, completionHandler: completionHandler)

        case NSURLAuthenticationMethodClientCertificate:
            // ← mTLS: server is asking US to prove identity
            handleClientCertificate(challenge, completionHandler: completionHandler)

        default:
            // Unknown method — reject it, don't fall back to defaults
            completionHandler(.cancelAuthenticationChallenge, nil)
        }
    }

    private func handleServerTrust(
        _ challenge: URLAuthenticationChallenge,
        completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void
    ) {
        // Step 1: Get the server's trust object
        guard let serverTrust = challenge.protectionSpace.serverTrust else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        // Step 2: Evaluate trust against system policy FIRST
        // This ensures cert is not expired, not revoked, chain is valid
        var error: CFError?
        let isSystemTrusted = SecTrustEvaluateWithError(serverTrust, &error)

        guard isSystemTrusted else {
            // Cert fails standard validation — definitely reject
            SecurityEventLogger.log(.certValidationFailed, host: challenge.protectionSpace.host)
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        // Step 3: Now do our custom pin check on top
        if CertificatePinner.shared.validate(serverTrust, host: challenge.protectionSpace.host) {
            completionHandler(.useCredential, URLCredential(trust: serverTrust))
        } else {
            SecurityEventLogger.log(.pinMismatch, host: challenge.protectionSpace.host)
            completionHandler(.cancelAuthenticationChallenge, nil)
        }
    }

    private func handleClientCertificate(
        _ challenge: URLAuthenticationChallenge,
        completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void
    ) {
        // For mTLS: load client cert from Keychain and present it
        guard let identity = KeychainManager.loadClientIdentity() else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }
        let credential = URLCredential(
            identity: identity,
            certificates: nil,
            persistence: .none   // never cache credentials
        )
        completionHandler(.useCredential, credential)
    }
}
QWhy can't you use URLSession.shared for certificate pinning?

URLSession.shared is created internally by Apple with a nil delegate. You cannot assign a delegate to it after creation — URLSession copies the delegate at init time and it's immutable. Since certificate pinning requires implementing URLSessionDelegate methods to intercept authentication challenges, you must create your own URLSession instance with your pinning delegate. Using the shared session in a fintech context means zero pinning — any certificate from any CA will be accepted, making MITM attacks trivial.

QWhat is the difference between timeoutIntervalForRequest and timeoutIntervalForResource?

timeoutIntervalForRequest is the maximum time to wait for any single packet of data to arrive. If the server sends a header but then goes silent for longer than this interval, the request fails. timeoutIntervalForResource is the total maximum time for the entire resource download from first byte to last byte. For a payment API, set request timeout short (30s) to fail fast on network issues. For a background KYC document upload, you'd set resource timeout longer (several minutes) to allow for large file transfers on slow connections.

TLS 1.3 — Complete Mechanics

Hard

Transport Layer Security (TLS) is the cryptographic protocol that secures your app's connection to your server. As a Lead iOS engineer at a payment company, you need to understand TLS not just as "the thing that makes the padlock appear" but at the protocol level — because every design decision you make around networking security rests on TLS.

What TLS Actually Does

TLS provides three guarantees:

  • Confidentiality — Data is encrypted so eavesdroppers see only ciphertext
  • Integrity — Data cannot be modified in transit without detection (via HMAC/AEAD)
  • Authentication — You can verify you're talking to the real server, not an impostor

Without all three, a payment app is broken. Confidentiality alone isn't enough — an attacker who can't read your data could still flip bits and corrupt a transaction amount.

TLS 1.3 Handshake — Step by Step

TLS 1.3 (RFC 8446, 2018) dramatically simplified the handshake compared to 1.2. The key innovation: the client sends its key share in the very first message, allowing the server to derive encryption keys immediately and encrypt its response. This eliminates a full round trip.

  │   • Supported cipher suites                   │

  │   • ECDH key_share (public key)  ← NEW in 1.3 │
  │   • Supported TLS versions                    │
  │                                               │
  │◄─── ServerHello ──────────────────────────────│
  │   • Chosen cipher suite                       │
  │   • Server random                             │
  │   • ECDH key_share (server public key)        │
  │                                               │
  │   ← Both sides now compute shared secret via ECDH
  │   ← Derive: handshake_secret, then master_secret
  │                                               │
  │◄═══ {EncryptedExtensions} ════════════════════│  ← Encrypted from here
  │◄═══ {Certificate} ════════════════════════════│

  │◄═══ {Finished} ═══════════════════════════════│  ← HMAC over handshake transcript

Perfect Forward Secrecy — Why It Matters for FinTech

PFS is the property where compromise of a server's long-term private key does not compromise past session keys. In TLS 1.3, this is achieved through ECDHE (Elliptic Curve Diffie-Hellman Ephemeral): each session generates a new ephemeral key pair, the shared secret is derived and immediately discarded, and neither party stores the session key.

Without PFS (as with RSA key exchange in TLS 1.2): an attacker records all encrypted FinTech traffic today. Later, they obtain the server's private key (data breach, court order, state actor). They can now decrypt every historical session — every transaction amount, every recipient phone number, every balance query — going back years.

With PFS: recorded historical traffic is permanently safe because the session keys no longer exist.

The Five TLS 1.3 Cipher Suites

TLS 1.3 ships only 5 cipher suites, all using AEAD (Authenticated Encryption with Associated Data) — meaning encryption and integrity check are combined in a single operation:

  • TLS_AES_128_GCM_SHA256 — AES 128-bit in GCM mode, SHA-256 for PRF
  • TLS_AES_256_GCM_SHA384 — AES 256-bit, SHA-384 (recommended for fintech)
  • TLS_CHACHA20_POLY1305_SHA256 — ChaCha20 stream cipher, better on mobile CPUs without AES-NI
  • TLS_AES_128_CCM_SHA256 — For constrained IoT devices
  • TLS_AES_128_CCM_8_SHA256 — Shorter auth tag, IoT only

For FinTech backend configuration, mandate TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256. Remove the CCM suites — they're for IoT, not fintech.

0-RTT Resumption — The Security Trade-off

TLS 1.3 introduced 0-RTT (zero round-trip) resumption: a returning client can send application data in its very first flight — before the handshake completes — using a pre-shared key (PSK) from the previous session. This eliminates the handshake latency entirely for repeat connections.

⚠️
Never Enable 0-RTT for Payment Endpoints 0-RTT data is vulnerable to replay attacks. An attacker who intercepts a 0-RTT request can re-send it verbatim. For a POST /transfer request, this could mean a transaction executes twice. Only use 0-RTT for safe, idempotent GET requests (e.g., static assets). All payment API endpoints must be 1-RTT minimum, and implement server-side nonce/idempotency key checks regardless.

QExplain the ECDH key exchange step. Why is it secure even if an attacker observes the public keys?

ECDH is based on the Elliptic Curve Discrete Logarithm Problem: given a point P on a curve and the result Q = nP (scalar multiplication), it is computationally infeasible to determine n. Both parties choose random private scalars (a, b), compute public points (A = aG, B = bG where G is the curve's base point), and exchange them. The shared secret is: client computes aB = a(bG) = abG, server computes bA = b(aG) = abG. Both arrive at abG without ever transmitting a or b. An attacker observing A and B cannot derive abG without solving the discrete log problem — infeasible for P-256 with current computing (would require more operations than atoms in the observable universe).

Certificate Pinning — All Three Methods

Expert

Certificate pinning is the practice of hardcoding cryptographic expectations about a server's certificate into your app, then validating those expectations during every TLS handshake. Standard TLS trusts any certificate signed by any CA in the device's trust store — which includes hundreds of CAs worldwide. If any one of those CAs is compromised or malicious, an attacker can obtain a valid certificate for your domain and perform a MITM attack that passes standard TLS validation silently.

Pinning breaks this assumption. Even with a valid CA-issued certificate, if it doesn't match your pin, the connection is rejected.

When Pinning Is Attacked

Without pinning, attackers use tools like Charles Proxy, mitmproxy, or Burp Suite. They install their own root CA certificate on the device (possible via MDM or social engineering) and their proxy then issues a "valid" cert for your domain that the device trusts. They see every request and response in plain text.

Method 1: Full Certificate Pinning

Pin the exact DER-encoded certificate. When the server presents its cert, compute its hash and compare against your stored hash. If it doesn't match exactly — reject.

  • Pro: Maximum specificity. Guaranteed to be the exact cert you vetted.
  • Con: Breaks the moment the server renews its certificate (typically every 90 days for Let's Encrypt, 1-2 years for others). Requires an app update to change the pin.
  • Use when: You control the certificate lifecycle tightly and have a rapid app update mechanism.
Swift — Method 1: Full Certificate Pinning
final class CertificatePinner {

    // Extract hash: openssl x509 -in cert.pem -outform der | openssl dgst -sha256 -binary | base64
    private let pinnedCertHashes: [String: [String]] = [
        "api.fintech.com": [
            "sha256/AAAA...currentCertHash...======",  // Current cert
            "sha256/BBBB...backupCertHash...======"   // Backup (pre-rotate)
        ]
    ]

    func validate(serverTrust: SecTrust, host: String) -> Bool {
        guard let pins = pinnedCertHashes[host] else {
            return false  // Unknown host — reject
        }

        // Get all certs in the chain (index 0 = leaf cert)
        let certCount = SecTrustGetCertificateCount(serverTrust)

        for i in 0..<certCount {
            guard let cert = SecTrustGetCertificateAtIndex(serverTrust, i) else { continue }

            // Get DER representation of the cert
            let certData = SecCertificateCopyData(cert) as Data

            // SHA-256 hash of the full certificate
            var hash = [UInt8](repeating: 0, count: Int(CC_SHA256_DIGEST_LENGTH))
            certData.withUnsafeBytes {
                _ = CC_SHA256($0.baseAddress, CC_LONG(certData.count), &hash)
            }
            let hashBase64 = "sha256/" + Data(hash).base64EncodedString()

            if pins.contains(hashBase64) { return true }
        }
        return false
    }
}

Method 2: Public Key Pinning (SPKI) — Recommended

Instead of pinning the full certificate, you pin only the SubjectPublicKeyInfo (SPKI) — the public key and its algorithm metadata. This survives certificate renewal as long as the key pair is reused. The SPKI is extracted, hashed with SHA-256, and the resulting hash is your pin.

To extract the SPKI hash from a live server:

Swift — Method 2: Public Key (SPKI) Pinning — Production Grade
import Foundation
import CryptoKit
import Security

final class SPKIPinner: NSObject, URLSessionDelegate {

    // Pinned SPKI SHA-256 hashes per host
    // Always pin at least 2: current + backup for seamless rotation
    private static let pins: [String: Set<String>] = [
        "api.fintech.com": [
            "47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=",  // current
            "CXVN1p2FqLGh7asDFdxf5Mg7xqxz7VBrKJpb4R3qZtY="   // backup
        ],
        "auth.fintech.com": [
            "M8HztckAkgkMNDWBnS8+mCsOy0tBHyNNDxOEhFGNh9I="
        ]
    ]

    // ASN.1 header bytes that prefix raw RSA-2048 key in SPKI format
    // These are standard — Apple's SecKeyCopyExternalRepresentation
    // returns the raw key WITHOUT the SPKI header, so we add it back
    private static let rsaHeaderBytes: [UInt8] = [
        0x30, 0x82, 0x01, 0x22, 0x30, 0x0d, 0x06, 0x09,
        0x2a, 0x86, 0x48, 0x86, 0xf7, 0x0d, 0x01, 0x01,
        0x01, 0x05, 0x00, 0x03, 0x82, 0x01, 0x0f, 0x00
    ]
    private static let ecHeaderBytes: [UInt8] = [
        0x30, 0x59, 0x30, 0x13, 0x06, 0x07, 0x2a, 0x86,
        0x48, 0xce, 0x3d, 0x02, 0x01, 0x06, 0x08, 0x2a,
        0x86, 0x48, 0xce, 0x3d, 0x03, 0x01, 0x07, 0x03,
        0x42, 0x00
    ]

    func urlSession(
        _ session: URLSession,
        didReceive challenge: URLAuthenticationChallenge,
        completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void
    ) {
        guard
            challenge.protectionSpace.authenticationMethod == NSURLAuthenticationMethodServerTrust,
            let serverTrust = challenge.protectionSpace.serverTrust
        else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        let host = challenge.protectionSpace.host

        // First: standard chain validation (expiry, revocation, CA chain)
        var cfError: CFError?
        guard SecTrustEvaluateWithError(serverTrust, &cfError) else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        // Second: our custom SPKI pin check
        guard validatePin(serverTrust: serverTrust, host: host) else {
            SecurityTelemetry.report(event: .pinFailure(host: host))
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        completionHandler(.useCredential, URLCredential(trust: serverTrust))
    }

    private func validatePin(serverTrust: SecTrust, host: String) -> Bool {
        guard let expectedPins = SPKIPinner.pins[host] else {
            return false  // No pins configured for host — fail closed
        }

        // Check leaf cert (index 0) — this is the server's own cert
        guard let serverCert = SecTrustGetCertificateAtIndex(serverTrust, 0),
              let publicKey = SecCertificateCopyKey(serverCert),
              let rawKeyData = SecKeyCopyExternalRepresentation(publicKey, nil) as Data?
        else { return false }

        // Determine key type to select correct ASN.1 header
        let keyType = SecKeyGetBlockSize(publicKey)  // rough size check
        let header: [UInt8] = keyType == 32  // P-256 = 32-byte keys
            ? SPKIPinner.ecHeaderBytes
            : SPKIPinner.rsaHeaderBytes

        // Reconstruct full SPKI: ASN.1 header + raw public key bytes
        var spki = Data(header)
        spki.append(rawKeyData)

        // SHA-256 hash → base64 → compare to stored pins
        let digest = SHA256.hash(data: spki)
        let hashString = Data(digest).base64EncodedString()

        return expectedPins.contains(hashString)
    }
}

Method 3: CA / Intermediate Pinning

Instead of pinning the leaf cert or its key, you pin the issuing CA or intermediate CA. Any cert from that CA for your domain is accepted.

  • Pro: Survives certificate renewals automatically. Good if you use a private CA you control.
  • Con: If the CA is compromised, attackers can issue valid certs for your domain. Less restrictive than leaf/key pinning.
  • Use when: You operate your own internal CA for all microservices.

Pin Rotation — The Critical Operational Challenge

The biggest risk of certificate pinning is "bricking" your app when your server certificate changes. A proper rotation strategy:

1
Always Pin N+1 Keys

Before rotating, generate the new key pair and embed both the current and future SPKI hash in the app. Ship this as an update.

2
Dynamic Pin Delivery (Optional)

Serve the next rotation's pin in a signed API response. App verifies the signature (using an embedded public key for the pin manifest) and updates its set of accepted pins.

3
Minimum App Version Enforcement

After rotation, reject connections from app versions older than the release that contained the new pin. Backend returns 426 Upgrade Required.

4
Emergency Disable

Have a kill switch: a server-signed flag that disables pinning enforcement, scoped to a time window, for catastrophic pin failure scenarios. This flag itself must be fetched from an alternate channel.

App Transport Security (ATS)

Medium

App Transport Security is Apple's mandatory network security policy, enforced since iOS 9. ATS blocks all HTTP connections and enforces minimum TLS standards. It is the first line of defense — configured in Info.plist — and operates before your URLSession code even runs.

ATS Default Behaviour (No Config Needed)

Out of the box, ATS enforces: HTTPS only, TLS 1.2 minimum, forward secrecy required (ECDHE), no SHA-1 certificates, 2048-bit RSA or 256-bit EC keys minimum. These defaults are good but not enough for a payment app. You should harden further.

ATS Configuration Hierarchy

ATS processes rules in this order: domain-specific exceptions → NSAllowsArbitraryLoads global setting → defaults. Think of it as a security policy whitelist.

Info.plist — Hardened ATS for FinTech
<!-- Info.plist — Production ATS configuration -->
<key>NSAppTransportSecurity</key>
<dict>

    <!-- NEVER set this to true in a fintech app -->
    <key>NSAllowsArbitraryLoads</key>
    <false/>

    <!-- Disable local network exceptions (blocks Charles Proxy MITM) -->
    <key>NSAllowsLocalNetworking</key>
    <false/>

    <key>NSExceptionDomains</key>
    <dict>

        <!-- Primary API domain -->
        <key>api.fintech.com</key>

Certificate Transparency (CT) is a public, append-only ledger where Certificate Authorities are required to log all certificates they issue. Any certificate not in a CT log is considered untrustworthy. This prevents "private" or rogue certificate issuance — if a CA issues a cert for fintech.com without logging it, CT enforcement will reject that connection. Setting NSRequiresCertificateTransparency to true makes iOS verify that the server's certificate appears in a valid CT log before allowing the connection. This is a major defense against CA compromise attacks.

Modern Swift Networking: Async/Await, Actors & Structured Concurrency

Hard

Swift's structured concurrency (SE-0296, SE-0306) transformed iOS networking. Before Swift 5.5, URLSession networking was callback-based, leading to callback hell, threading bugs, and data races. Modern Swift gives us async/await for readable code, Actor for data-race-free shared state, and Task for structured, cancellable work units.

For a Lead iOS engineer, the expectation is not just knowing the syntax but understanding the concurrency model and why it matters for security-sensitive code like session management and token refresh.

The Classic Problem: Double Token Refresh Race Condition

Without proper concurrency handling, this bug appears in every payment app that uses refresh tokens:

Race Condition Scenario
Two concurrent network requests (e.g., balance check + transaction history) both fail with 401 Unauthorized at the same time. Both detect "token expired" and both trigger a refresh. Two refresh calls go to the server simultaneously. The server issues two new tokens and invalidates two old refresh tokens. One response arrives first and stores a new refresh token. The second response stores a different refresh token, overwriting the first. Now the first token response is orphaned. Next request fails. User is logged out. This is a common bug in fintech apps and a nightmare to debug.
Swift — Production Network Layer with Actor-Isolated Session Management
import Foundation

// ── Error types ──────────────────────────────────────
enum NetworkError: Error, LocalizedError {
    case invalidURL
    case invalidResponse
    case httpError(Int, data: Data?)
    case decodingError(Error)
    case unauthorized   // 401 — triggers token refresh
    case forbidden      // 403 — session revoked, must re-login
    case pinningFailure // Certificate pin mismatch
}

// ── Token storage (Actor = thread-safe) ──────────────
actor TokenStore {
    private var accessToken: String?
    private var expiresAt: Date?
    private var refreshTask: Task<String, Error>?  // serialises concurrent refreshes

    func setToken(_ token: String, expiresIn: TimeInterval) {
        self.accessToken = token
        self.expiresAt   = Date().addingTimeInterval(expiresIn - 60)  // 60s buffer
        self.refreshTask = nil  // clear any in-flight refresh
    }

    func clearToken() {
        accessToken = nil; expiresAt = nil; refreshTask = nil
    }

    // Returns valid token, refreshing if expired
    // KEY: if a refresh is already in-flight, ALL callers await the SAME task
    // This eliminates the double-refresh race condition entirely
    func validToken(using refresher: TokenRefresher) async throws -> String {
        // Token still fresh?
        if let token = accessToken,
           let expiry = expiresAt, expiry > Date() {
            return token
        }

        // Is a refresh already in-flight?
        if let existing = refreshTask {
            return try await existing.value   // join the existing refresh
        }

        // No token & no in-flight refresh — start one
        let task = Task<String, Error> {
            let refreshToken = try KeychainService.load(key: .refreshToken)
            let response = try await refresher.refresh(token: refreshToken)
            // Store new tokens
            try KeychainService.save(response.refreshToken, key: .refreshToken)
            await self.setToken(response.accessToken, expiresIn: response.expiresIn)
            return response.accessToken
        }
        self.refreshTask = task

        do {
            return try await task.value
        } catch {
            self.refreshTask = nil
            throw error
        }
    }
}

// ── Generic API client ────────────────────────────────
actor APIClient {
    private let session: URLSession
    private let tokenStore: TokenStore
    private let baseURL = URL(string: "https://api.fintech.com/v3")!
    private let decoder = JSONDecoder()

    init(tokenStore: TokenStore) {
        self.tokenStore = tokenStore
        decoder.dateDecodingStrategy = .iso8601
        decoder.keyDecodingStrategy = .convertFromSnakeCase

        let config = URLSessionConfiguration.ephemeral
        config.requestCachePolicy = .reloadIgnoringLocalAndRemoteCacheData
        self.session = URLSession(
            configuration: config,
            delegate: SPKIPinner(),  // our pinning delegate
            delegateQueue: nil
        )
    }

    func request<T: Decodable>(
        endpoint: Endpoint,
        responseType: T.Type,
        retryOn401: Bool = true
    ) async throws -> T {
        var urlRequest = try endpoint.urlRequest(baseURL: baseURL)

        // Attach fresh access token
        let token = try await tokenStore.validToken(using: AuthRefresher())
        urlRequest.setValue("Bearer \(token)", forHTTPHeaderField: "Authorization")

        // Add request ID for server-side idempotency
        urlRequest.setValue(UUID().uuidString, forHTTPHeaderField: "X-Request-ID")

        let (data, response) = try await session.data(for: urlRequest)

        guard let http = response as? HTTPURLResponse else {
            throw NetworkError.invalidResponse
        }

        switch http.statusCode {
        case 200...299:
            return try decoder.decode(T.self, from: data)

        case 401 where retryOn401:
            // Token expired mid-request — clear it and retry once
            await tokenStore.clearToken()
            return try await request(endpoint: endpoint,
                                          responseType: responseType,
                                          retryOn401: false)  // no more retries

        case 401:
            throw NetworkError.unauthorized  // show login screen

        case 403:
            await tokenStore.clearToken()
            throw NetworkError.forbidden     // force re-login

        default:
            throw NetworkError.httpError(http.statusCode, data: data)
        }
    }
}

QWhy is an Actor better than a DispatchQueue with a barrier flag for the token store?

Both Actor and a serial DispatchQueue provide mutual exclusion. But Actor wins on three fronts: (1) Compile-time enforcement — the Swift compiler rejects code that accesses actor-isolated state from outside the actor without await. A DispatchQueue is a runtime mechanism with no compile-time guarantees — you can forget the queue.async call and create a race condition that the compiler won't catch. (2) Async-aware — Actors integrate with Swift's structured concurrency. When Actor code awaits a suspension point, it yields its thread — other Actors can run. A DispatchQueue with a serial queue would block that thread. (3) No callback inversion — actor methods are called with await, preserving linear code flow. DispatchQueue forces either callback nesting or complex semaphore gymnastics.

Keychain Services — Deep Dive

Hard

The iOS Keychain is a hardware-encrypted, OS-managed secure storage system. Unlike a database or UserDefaults (which are just files in your sandbox), Keychain items are encrypted with keys derived from the device's UID (a key fused into the hardware at manufacturing) and, optionally, the user's passcode. This means Keychain data is inaccessible without the correct device even if someone physically extracts the flash storage chips.

How Keychain Encryption Works

Every Keychain item is wrapped by a per-item key. That per-item key is encrypted by a class key. The class key is derived from the device UID (always available) and optionally the user's passcode (only available when unlocked). This is the Data Protection hierarchy. The kSecAttrAccessible attribute selects which class key is used — determining when the item can be decrypted.

Accessibility Classes — Choose Correctly

AfterFirstUnlock After first unlock (even locked) Yes Yes Background tasks only
AfterFirstUnlockThisDeviceOnly After first unlock (even locked) No No Push notification processing
Always (deprecated) Always — even locked Yes Yes 🚫 Never use

    case encodingFailed
    case saveFailed(OSStatus)
    case loadFailed(OSStatus)

final class KeychainService {

    private static let service = "com.fintech.ios"
    private static let accessGroup = "TEAMID.com.fintech.shared" // for app extensions

    // ── SAVE ────────────────────────────────────────────
    static func save(_ value: String, key: KeychainKey) throws {
        guard let data = value.data(using: .utf8) else {
            throw KeychainError.encodingFailed
        }
        try saveData(data, key: key)
    }

    static func saveData(_ data: Data, key: KeychainKey) throws {
        // Delete existing item first to avoid duplicate item error (-25299)
        deleteIfExists(key: key)

        let query: [CFString: Any] = [
            kSecClass:               kSecClassGenericPassword,
            kSecAttrService:         service,
            kSecAttrAccount:         key.rawValue,
            kSecValueData:           data,

            // ThisDeviceOnly = no iCloud sync, no backup, no migration
            kSecAttrAccessible:      kSecAttrAccessibleWhenUnlockedThisDeviceOnly,

            // Block iCloud Keychain sync explicitly
            kSecAttrSynchronizable:  kCFBooleanFalse!,

            // Shared group for app + notification extension access
            kSecAttrAccessGroup:     accessGroup
        ]

        let status = SecItemAdd(query as CFDictionary, nil)
        guard status == errSecSuccess else {
            throw KeychainError.saveFailed(status)
        }
    }

    // ── LOAD ────────────────────────────────────────────
    static func load(key: KeychainKey) throws -> String {
        let data = try loadData(key: key)
        guard let string = String(data: data, encoding: .utf8) else {
            throw KeychainError.encodingFailed
        }
        return string
    }

    static func loadData(key: KeychainKey) throws -> Data {
        let query: [CFString: Any] = [
            kSecClass:              kSecClassGenericPassword,
            kSecAttrService:        service,
            kSecAttrAccount:        key.rawValue,
            kSecReturnData:         kCFBooleanTrue!,
            kSecMatchLimit:         kSecMatchLimitOne,
            kSecAttrSynchronizable: kCFBooleanFalse!
        ]

        var result: AnyObject?
        let status = SecItemCopyMatching(query as CFDictionary, &result)

        guard status == errSecSuccess,
              let data = result as? Data
        else {
            if status == errSecItemNotFound {
                throw KeychainError.itemNotFound
            }
            throw KeychainError.loadFailed(status)
        }
        return data
    }

    // ── DELETE ──────────────────────────────────────────
    @discardableResult
    static func delete(key: KeychainKey) -> Bool {
        let query: [CFString: Any] = [
            kSecClass:       kSecClassGenericPassword,
            kSecAttrService: service,
            kSecAttrAccount: key.rawValue
        ]
        return SecItemDelete(query as CFDictionary) == errSecSuccess
    }

    private static func deleteIfExists(key: KeychainKey) {
        delete(key: key) // discard result intentionally
    }

    // ── BIOMETRIC-GATED ITEM ────────────────────────────
    // Storing an item that requires Face ID / Touch ID to read
    static func saveBiometric(_ data: Data, key: KeychainKey) throws {
        deleteIfExists(key: key)

        // .biometryCurrentSet: item invalidated if biometry enrollment changes
        // This prevents a thief adding their fingerprint to access the item
        guard let access = SecAccessControlCreateWithFlags(
            nil,
            kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly,
            [.biometryCurrentSet],  // or .userPresence if you want passcode fallback
            nil
        ) else { throw KeychainError.encodingFailed }

        let query: [CFString: Any] = [
            kSecClass:               kSecClassGenericPassword,
            kSecAttrService:         service,
            kSecAttrAccount:         key.rawValue,
            kSecValueData:           data,
            kSecAttrAccessControl:   access,
            kSecAttrSynchronizable:  kCFBooleanFalse!
            // Note: no kSecAttrAccessible here — AccessControl takes precedence
        ]

        let status = SecItemAdd(query as CFDictionary, nil)
        guard status == errSecSuccess else {
            throw KeychainError.saveFailed(status)
        }
    }

    // ── WIPE ON LOGOUT ──────────────────────────────────
    static func wipeSessionData() {
        [KeychainKey.accessToken, .refreshToken, .mfaSecret]
            .forEach { delete(key: $0) }
    }
}

Cryptography: AES-GCM, RSA, ECDH, HMAC

Expert

Apple's CryptoKit framework (iOS 13+) provides a modern, type-safe Swift API for cryptographic operations. It's built on top of the same battle-tested cryptographic libraries used by the OS itself. For a payment app, you need to understand not just how to call these APIs but why each algorithm is chosen, what its security properties are, and what attacks it prevents or is vulnerable to.

Symmetric Encryption: AES-GCM

AES (Advanced Encryption Standard) is the global standard for symmetric encryption. AES-GCM (Galois/Counter Mode) is an AEAD (Authenticated Encryption with Associated Data) mode — it simultaneously provides confidentiality, integrity, and authenticity in a single operation. This is what you use for encrypting local data or API payloads.

Why AES-GCM over AES-CBC?

AES-CBC is an older mode that provides confidentiality only. You'd need a separate HMAC to detect tampering — and getting this composition right is notoriously error-prone. CBC is also vulnerable to padding oracle attacks (demonstrated by POODLE, BEAST, Lucky 13). GCM's authentication tag catches any modification of the ciphertext — if even one bit changes, decryption fails with an authentication error.

AES-GCM Internals
Components of a sealed box:
• Nonce (12 bytes): unique initialization value. Never reuse with the same key.
• Ciphertext: AES-CTR encrypted plaintext (same length as plaintext)
• Authentication Tag (16 bytes): GHASH over nonce + ciphertext + associated data

Associated Data (AD): Data that is authenticated but NOT encrypted. Use it for metadata that must travel alongside the ciphertext — e.g., transaction ID, timestamp, recipient. The tag covers the AD, so any tampering of the metadata is detected.
Swift — AES-GCM: Full Encryption/Decryption with Associated Data
import CryptoKit
import Foundation

// ── Data model for encrypted payload ─────────────────
struct EncryptedPayload: Codable {
    let nonce:      Data   // 12 bytes — MUST be unique per encryption
    let ciphertext: Data   // same length as plaintext
    let tag:        Data   // 16 bytes — authentication tag
    let keyId:      String // identifies which key version was used
}

enum CryptoService {

    // ── KEY GENERATION / DERIVATION ───────────────────

    // Generate a random 256-bit AES key
    static func generateKey() -> SymmetricKey {
        SymmetricKey(size: .bits256)  // 32 bytes = AES-256
    }

    // Derive a key from a passphrase using PBKDF2
    // Use this for PIN-based encryption (e.g., backup encryption)
    static func deriveKey(from passphrase: String, salt: Data) -> SymmetricKey {
        let rawKey = PBKDF2.deriveKey(
            from: passphrase.data(using: .utf8)!,
            salt: salt,
            using: .sha256,
            rounds: 310_000,  // OWASP 2023 recommendation
            outputByteCount: 32
        )
        return SymmetricKey(data: rawKey)
    }

    // ── ENCRYPTION ───────────────────────────────────
    static func encrypt(
        _ plaintext: Data,
        key: SymmetricKey,
        associatedData: Data? = nil,
        keyId: String = "v1"
    ) throws -> EncryptedPayload {

        // CryptoKit generates a cryptographically random nonce automatically
        // NEVER construct a nonce manually or reuse one
        let nonce = try AES.GCM.Nonce()

        let sealedBox = try AES.GCM.seal(
            plaintext,
            using: key,
            nonce: nonce,
            authenticating: associatedData ?? Data()
            // The AD is NOT encrypted but IS authenticated.
            // Any tampering of AD causes decryption to fail.
        )

        return EncryptedPayload(
            nonce:      Data(nonce),
            ciphertext: sealedBox.ciphertext,
            tag:        sealedBox.tag,
            keyId:      keyId
        )
    }

    // ── DECRYPTION ───────────────────────────────────
    static func decrypt(
        _ payload: EncryptedPayload,
        key: SymmetricKey,
        associatedData: Data? = nil
    ) throws -> Data {

        let nonce = try AES.GCM.Nonce(data: payload.nonce)

        let sealedBox = try AES.GCM.SealedBox(
            nonce:      nonce,
            ciphertext: payload.ciphertext,
            tag:        payload.tag
        )

        // If tag verification fails (tampered data), this throws
        // CryptoKitError.authenticationFailure — DO NOT ignore this error
        return try AES.GCM.open(
            sealedBox,
            using: key,
            authenticating: associatedData ?? Data()
        )
    }

    // ── HMAC — Message Authentication ─────────────────
    // Use when you need to authenticate data WITHOUT encrypting it
    // e.g., API request signing, webhook verification
    static func sign(_ data: Data, key: SymmetricKey) -> Data {
        let mac = HMAC<SHA256>.authenticationCode(for: data, using: key)
        return Data(mac)
    }

    static func verify(_ data: Data, signature: Data, key: SymmetricKey) -> Bool {
        // HMAC.isValidAuthenticationCode performs CONSTANT-TIME comparison
        // This prevents timing attacks that could leak signature bytes
        HMAC<SHA256>.isValidAuthenticationCode(
            signature,
            authenticating: data,
            using: key
        )
    }
}

// ── Real-world usage: encrypting a transaction before local storage

import CryptoKit

// ── End-to-End Encrypted Session Setup ───────────────
// Scenario: establishing an encrypted channel between iOS client and server
// for high-security operations like PIN change or device registration

enum E2ESession {

    struct ClientKeyPair {
        let privateKey: P256.KeyAgreement.PrivateKey
        var publicKeyData: Data { privateKey.publicKey.rawRepresentation }
    }

    // Step 1: Client generates ephemeral key pair
    static func generateClientKeys() -> ClientKeyPair {
        ClientKeyPair(privateKey: .init())
        // privateKey is ephemeral — lives only for this session
        // publicKeyData is sent to server in the session initiation request
    }

    // Step 2: After server sends back ITS public key,
    // derive a shared symmetric key using ECDH + HKDF
    static func deriveSessionKey(
        clientKeys: ClientKeyPair,
        serverPublicKeyData: Data,
        sessionId: String   // used as HKDF context info for domain separation
    ) throws -> SymmetricKey {

        let serverPublicKey = try P256.KeyAgreement.PublicKey(
            rawRepresentation: serverPublicKeyData
        )

        // ECDH: compute shared secret
        // Both client and server compute this independently and get the SAME result
        // Nobody else can compute it — it requires one of the private keys
        let sharedSecret = try clientKeys.privateKey
            .sharedSecretFromKeyAgreement(with: serverPublicKey)

        // HKDF (HMAC-based Key Derivation Function) — RFC 5869
        // Derives a cryptographically strong key from the shared secret
        // WHY NOT USE RAW SECRET? The raw ECDH output has structure that
        // makes it unsuitable as a direct AES key. HKDF "stretches" and
        // "randomizes" it into a uniform 256-bit key.
        let sessionKey = sharedSecret.hkdfDerivedSymmetricKey(
            using: SHA256.self,
            salt:  "fintech-e2e-v1".data(using: .utf8)!,
            sharedInfo: sessionId.data(using: .utf8)!,  // domain separation
            outputByteCount: 32  // 256-bit AES-GCM key
        )

        // Now both client and server can encrypt/decrypt with this key
        // using AES-GCM — see CryptoService.encrypt() above
        return sessionKey
    }

    // ── DERIVING MULTIPLE KEYS FROM ONE SECRET ────────
    // Never use the same key for both encryption and signing
    // Derive separate keys for different purposes:
    static func deriveAllKeys(
        from sharedSecret: SharedSecret
    ) -> (encryptionKey: SymmetricKey, signingKey: SymmetricKey) {

        let salt = "fintech-session-salt-v1".data(using: .utf8)!

        let encKey = sharedSecret.hkdfDerivedSymmetricKey(
            using: SHA256.self, salt: salt,
            sharedInfo: "encryption".data(using: .utf8)!,
            outputByteCount: 32
        )
        let sigKey = sharedSecret.hkdfDerivedSymmetricKey(
            using: SHA256.self, salt: salt,
            sharedInfo: "signing".data(using: .utf8)!,
            outputByteCount: 32
        )
        return (encKey, sigKey)
    }
}

Secure Enclave — Hardware Root of Trust

Expert

The Secure Enclave is a dedicated security coprocessor present in all Apple devices with an A7 chip or later (iPhone 5s+, all modern devices). It has its own encrypted memory, its own boot ROM, its own random number generator, and its own cryptographic engine. Crucially: the Secure Enclave's private keys never leave the chip. Not even the main CPU can access them.

What Makes It Special

When you generate a P256 private key in the Secure Enclave, the raw key material is generated inside the enclave and never exits. When you perform a signing operation, the data to be signed is sent into the enclave, the signing happens inside, and only the signature comes out. An attacker with full root access to iOS, a sophisticated malware, or even a rogue app cannot extract the private key from the enclave.

Secure Enclave vs. Keychain

Regular Keychain items are encrypted with hardware-derived keys but the key material itself can potentially be read if the device encryption is bypassed. Secure Enclave keys are generated and used exclusively inside the coprocessor — there is no software path to access the raw key, even for Apple's OS.

What You CAN Do with Secure Enclave Keys

  • Generate P256 ECDSA key pairs for signing (SE-backed)
  • Generate P256 ECDH key pairs for key agreement
  • Sign data (data goes in, signature comes out)
  • Protect keys with biometric authentication (Face ID gates the operation)
  • Get the opaque key data representation for storage (this is NOT the raw key — it's a handle)

What you cannot do: use RSA or other algorithms (P256 only in SE), use keys without biometric if you set that constraint, or extract the raw key bytes.

import LocalAuthentication

enum SecureEnclaveManager {

    // ── Key tag for Keychain storage of the SE key reference ──
    private static let keyTag = "com.fintech.transaction-signing-key".data(using: .utf8)!

    // ── GENERATE OR LOAD signing key ─────────────────────────
    static func signingKey() throws -> SecureEnclave.P256.Signing.PrivateKey {
        // Try loading existing key first
        if let existing = try? loadKey() { return existing }

        // Generate new key if not found
        return try generateKey()
    }

    private static func generateKey() throws
        -> SecureEnclave.P256.Signing.PrivateKey
    {
        // Access control: biometry required, item deleted if biometry changes
        // This ensures security even if the user's device is stolen and the thief
        // tries to add their own fingerprint
        let access = SecAccessControlCreateWithFlags(
            kCFAllocatorDefault,
            kSecAttrAccessibleWhenUnlockedThisDeviceOnly,
            [.privateKeyUsage, .biometryCurrentSet],
            nil
        )!

        let privateKey = try SecureEnclave.P256.Signing.PrivateKey(
            accessControl: access
        )

        // Store the DATA REPRESENTATION (opaque handle, NOT the raw key)
        // in Keychain so we can reload the key reference later
        try storeKeyData(privateKey.dataRepresentation)

        return privateKey
    }

    private static func loadKey() throws
        -> SecureEnclave.P256.Signing.PrivateKey
    {
        let query: [CFString: Any] = [
            kSecClass:            kSecClassKey,
            kSecAttrApplicationTag: keyTag,
            kSecAttrKeyType:      kSecAttrKeyTypeECSECPrimeRandom,
            kSecReturnData:       kCFBooleanTrue!,
            kSecMatchLimit:       kSecMatchLimitOne
        ]
        var result: AnyObject?
        let status = SecItemCopyMatching(query as CFDictionary, &result)
        guard status == errSecSuccess, let data = result as? Data else {
            throw KeychainError.itemNotFound
        }

        // Reconstruct the SE key from its opaque data representation
        // This re-connects to the Secure Enclave hardware key
        return try SecureEnclave.P256.Signing.PrivateKey(
            dataRepresentation: data
        )
    }

    private static func storeKeyData(_ data: Data) throws {
        let query: [CFString: Any] = [
            kSecClass:              kSecClassKey,
            kSecAttrApplicationTag: keyTag,
            kSecAttrKeyType:        kSecAttrKeyTypeECSECPrimeRandom,
            kSecValueData:          data,
            kSecAttrSynchronizable: kCFBooleanFalse!
        ]
        SecItemDelete(query as CFDictionary)
        let status = SecItemAdd(query as CFDictionary, nil)
        guard status == errSecSuccess else { throw KeychainError.saveFailed(status) }
    }

    // ── SIGN A TRANSACTION ────────────────────────────────────
    // Face ID / Touch ID prompt fires automatically during this call
    static func signTransaction(_ payload: TransactionPayload)
        async throws -> SignedTransaction
    {
        // Build canonical bytes: deterministic, covers all fields
        let canonical = payload.canonicalRepresentation()

        // This call triggers biometric prompt in the Secure Enclave
        // The signing happens INSIDE the enclave — raw key never exits
        let privateKey = try signingKey()
        let signature  = try privateKey.signature(for: canonical)

        return SignedTransaction(
            payload:   payload,
            signature: signature.derRepresentation,  // DER-encoded for API transmission
            publicKey: privateKey.publicKey.rawRepresentation
        )
    }

    // ── VERIFY (typically done server-side, but testable client-side)
    static func verify(
        transaction: SignedTransaction,
        publicKeyData: Data
    ) throws -> Bool {
        let pubKey = try P256.Signing.PublicKey(rawRepresentation: publicKeyData)
        let sig    = try P256.Signing.ECDSASignature(derRepresentation: transaction.signature)
        return pubKey.isValidSignature(sig, for: transaction.payload.canonicalRepresentation())
    }

    // ── DELETE KEY (on logout or account deletion)
    static func deleteKey() {
        let query: [CFString: Any] = [
            kSecClass:              kSecClassKey,
            kSecAttrApplicationTag: keyTag
        ]
        SecItemDelete(query as CFDictionary)
        // Note: the SE hardware key is also invalidated when its data representation
        // is deleted — the SE won't service signing requests without the handle
    }
}

// ── TransactionPayload canonical representation
struct TransactionPayload: Codable {
    let txId:        String
    let amount:      Int64    // in paisa — avoid floating point for money
    let recipient:   String
    let timestamp:   Int64    // Unix timestamp
    let nonce:       String  // server-provided, prevents replay attacks
    let deviceId:    String

    func canonicalRepresentation() -> Data {
        // Deterministic — same inputs always produce same bytes
        // Format: pipe-separated, amounts as integer strings (no locale-dependent formatting)
        let s = "\(txId)|\(amount)|\(recipient)|\(timestamp)|\(nonce)|\(deviceId)"
        return s.data(using: .utf8)!
    }
}

Jailbreak & Tampering Detection

Hard

A jailbroken iOS device has had its security model broken. The sandbox is bypassed, unsigned code runs freely, and tools like Frida can hook into any function in any app at runtime. For a payment app, a jailbroken device is a hostile environment — you cannot trust anything running on it.

What Attackers Can Do on a Jailbroken Device

  • Hook certificate pinning checks to always return success
  • Read Keychain items belonging to your app
  • Intercept and modify network requests via SSL Kill Switch
  • Dump the app binary and reverse engineer business logic
  • Modify memory at runtime to change transaction amounts, skip authentication
  • Intercept LocalAuthentication callbacks to fake biometric success

Detection Signals — Layer These

No single check is reliable — each can be bypassed individually. The strategy is to use many diverse checks so bypassing all of them becomes prohibitively expensive.

Swift — Multi-Signal Jailbreak Detection
import Foundation
import UIKit
import Darwin  // for fork(), sysctl()

final class JailbreakDetector {

    // Returns true if the device shows jailbreak signals
    // Call during app launch AND before each transaction
    static func isCompromised() -> Bool {
        // Run all checks — collect results for telemetry even if partial
        let checks: [(name: String, result: Bool)] = [
            ("filesystem",    checkFilesystem()),
            ("sandbox",       checkSandboxEscape()),
            ("dylibs",        checkSuspiciousLibraries()),
            ("fork",          checkForkCapability()),
            ("symlinks",      checkCriticalSymlinks()),
            ("schemes",       checkJailbreakSchemes()),
            ("debugger",      checkDebuggerAttached()),
            ("integrity",     checkCodeIntegrity())
        ]

        let triggered = checks.filter { $0.result }
        if !triggered.isEmpty {
            // Log to security telemetry (don't alert user yet — observe first)
            SecurityTelemetry.report(.jailbreakDetected(signals: triggered.map { $0.name }))
        }
        return !triggered.isEmpty
    }

    // ── CHECK 1: Known Jailbreak Files ───────────────────────
    private static func checkFilesystem() -> Bool {
        let jbPaths = [
            "/Applications/Cydia.app",
            "/Applications/Sileo.app",
            "/Applications/Zebra.app",
            "/usr/sbin/sshd",
            "/usr/bin/ssh",
            "/etc/apt",
            "/bin/bash",
            "/usr/lib/libhooker.dylib",     // Libhooker hooking lib
            "/usr/lib/libjailbreak.dylib",   // Jailbreak helper
            "/var/jb",                        // Rootless jailbreak path
            "/var/lib/dpkg/info",
            "/.bootstrapped_electra",
            "/jb/lzma"
        ]
        return jbPaths.contains { FileManager.default.fileExists(atPath: $0) }
    }

    // ── CHECK 2: Sandbox Escape (write outside container) ────
    private static func checkSandboxEscape() -> Bool {
        // Apps cannot write to /private/var on non-jailbroken devices
        let testPath = "/private/var/mobile/jb_write_test_\(arc4random())"
        do {
            try "test".write(toFile: testPath, atomically: true, encoding: .utf8)
            try? FileManager.default.removeItem(atPath: testPath)
            return true  // Write succeeded — sandbox breached
        } catch {
            return false  // Write failed as expected — sandbox intact
        }
    }

    // ── CHECK 3: Injected Hooking Libraries ──────────────────
    private static func checkSuspiciousLibraries() -> Bool {
        let suspiciousLibs = [
            "SubstrateLoader",    // Cydia Substrate / Substitute
            "cycript",            // Cycript runtime manipulation
            "libhooker",          // LibHooker
            "frida",              // Frida dynamic instrumentation
            "cynject",
            "SSLKillSwitch",      // Certificate pinning bypass
            "TweakInject"
        ]

        let imageCount = _dyld_image_count()
        for i in 0..<UInt32(imageCount) {
            if let name = _dyld_get_image_name(i) {
                let imgName = String(cString: name).lowercased()
                if suspiciousLibs.contains(where: { imgName.contains($0.lowercased()) }) {
                    return true
                }
            }
        }
        return false
    }

    // ── CHECK 4: Fork Capability ─────────────────────────────
    // App Store apps don't have the fork entitlement
    // fork() succeeds on jailbroken devices
    private static func checkForkCapability() -> Bool {
        let pid = fork()
        if pid >= 0 {
            if pid > 0 { kill(pid, SIGTERM) }  // kill child process
            return true  // fork() succeeded — compromised
        }
        return false
    }

    // ── CHECK 5: Symlinks in Critical Paths ──────────────────
    // On jailbroken devices, /Applications is a symlink to /var/stash
    private static func checkCriticalSymlinks() -> Bool {
        let symPaths = ["/Applications", "/Library/Ringtones",
                        "/Library/Wallpaper", "/usr/arm-apple-darwin9"]
        return symPaths.contains {
            (try? FileManager.default.destinationOfSymbolicLink(atPath: $0)) != nil
        }
    }

    // ── CHECK 6: Jailbreak URL Schemes ───────────────────────
    private static func checkJailbreakSchemes() -> Bool {
        let schemes = ["cydia://", "sileo://", "zbra://"]
        return schemes.contains {
            UIApplication.shared.canOpenURL(URL(string: $0)!)
        }
    }

    // ── CHECK 7: Debugger Attached ───────────────────────────
    private static func checkDebuggerAttached() -> Bool {
        var info = kinfo_proc()
        var size = MemoryLayout<kinfo_proc>.stride
        var mib: [Int32] = [CTL_KERN, KERN_PROC, KERN_PROC_PID, getpid()]
        let result = sysctl(&mib, u_int(mib.count), &info, &size, nil, 0)
        guard result == 0 else { return false }
        return (info.kp_proc.p_flag & P_TRACED) != 0
    }

    // ── CHECK 8: Code Signing Integrity ─────────────────────
    private static func checkCodeIntegrity() -> Bool {
        // Check if main executable's code signature is valid
        var csFlags: UInt32 = 0
        let status = csops(getpid(), CS_OPS_STATUS, &csFlags,
                          MemoryLayout<UInt32>.size)
        if status != 0 { return true }  // Failed to get status — suspicious

        // CS_VALID: signature is valid. CS_HARD: processes cannot disable enforcement
        let requiredFlags: UInt32 = 0x1  // CS_VALID
        return (csFlags & requiredFlags) == 0  // invalid signature = compromised
    }
}

Biometric Authentication — LocalAuthentication Deep Dive

Medium

LocalAuthentication (LA) is Apple's framework for requesting Face ID and Touch ID. For a payment app, biometrics serve two purposes: (1) UX — convenient authentication without PIN entry, and (2) Security — when combined with the Secure Enclave (as shown above), proof of user presence at the hardware level.

The Critical Distinction: LA-only vs LA + Secure Enclave

Using LAContext alone to "authenticate" a user is weak — the result is a boolean from the LA framework, which can be manipulated on a jailbroken device by hooking the callback. Pairing LA with Secure Enclave is strong — the biometric result gates access to a hardware operation that produces a cryptographic artifact. You cannot fake the artifact.

Swift — Biometric Auth: Correct Implementation
import LocalAuthentication

enum BiometricService {

    // ── CHECK AVAILABILITY ───────────────────────────────────
    static func availableBiometryType() -> LABiometryType {
        let ctx = LAContext()
        var error: NSError?
        guard ctx.canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics,
                                      error: &error) else {
            return .none
        }
        return ctx.biometryType  // .faceID, .touchID, or .none
    }

    // ── AUTHENTICATE WITH FALLBACK ───────────────────────────
    // For UI-level authentication (e.g., unlocking the app)
    // WARNING: This is NOT sufficient for authorizing transactions
    static func authenticate(reason: String) async throws -> Bool {
        let context = LAContext()

        // Prevent reuse of a previous successful evaluation
        context.touchIDAuthenticationAllowableReuseDuration = 0

        // Policy options:
        // .deviceOwnerAuthenticationWithBiometrics — biometrics ONLY, no passcode fallback
        // .deviceOwnerAuthentication — biometrics with passcode fallback
        // For payments: use biometrics-only, fall back gracefully to PIN re-entry in your app
        return try await withCheckedThrowingContinuation { cont in
            context.evaluatePolicy(
                .deviceOwnerAuthenticationWithBiometrics,
                localizedReason: reason
            ) { success, error in
                if let error { cont.resume(throwing: error) }
                else        { cont.resume(returning: success) }
            }
        }
    }

    // ── BIOMETRY CHANGE DETECTION ────────────────────────────
    // Detect if new fingerprints/faces were enrolled — security signal
    static func hasBiometryChanged() -> Bool {
        let context = LAContext()
        var error: NSError?
        context.canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics, error: &error)

        let defaults = UserDefaults.standard
        let storedDomain = defaults.object(forKey: "biometryDomain") as? NSData
        let currentDomain = context.evaluatedPolicyDomainState

        if let stored = storedDomain,
           let current = currentDomain,
           stored != current as NSData {
            return true  // Biometry enrollment changed!
        }

        // Store current domain state for future comparison
        defaults.set(currentDomain, forKey: "biometryDomain")
        return false
    }
}

// ── SECURE PATTERN: Transaction Authorization ────────────
// The RIGHT way to use biometrics in a payment flow:
// Biometrics gates a Secure Enclave signing operation
func authorizeTransaction(_ tx: TransactionPayload) async throws -> SignedTransaction {
    // Step 1: Check device integrity
    guard !JailbreakDetector.isCompromised() else {
        throw SecurityError.compromisedDevice
    }

    // Step 2: Detect biometry changes (new fingerprint added = security alert)
    if BiometricService.hasBiometryChanged() {
        await forceReAuthentication()  // require PIN re-entry
        SecurityTelemetry.report(.biometryEnrollmentChanged)
    }

    // Step 3: Sign with Secure Enclave (biometric prompt fires inside)
    // The biometric is enforced by HARDWARE, not by our code
    // Even if an attacker hooks LAContext callbacks, the SE won't sign
    // without valid biometric hardware confirmation
    return try await SecureEnclaveManager.signTransaction(tx)
}

PCI-DSS for Mobile — What Applies to iOS Code

Expert

PCI DSS v4.0 is the security standard for any system handling payment card data. Your iOS code is in scope if it touches card numbers, expiry dates, or CVVs. The golden rule: minimize cardholder data (CHD) your app ever sees. Every requirement only applies to systems in scope — narrow the scope, narrow your obligations.

Key Requirements That Touch Your iOS Code Directly

Req 3 — Protect Stored Cardholder Data
iOS impact: Never store PAN on device. Display truncated (last 4 digits only). Never store CVV under any circumstance. Fix: Tokenization — app stores a payment token, never the real card number. Fetch sensitive display data from server on demand inside a secure view.
Req 4 — Encrypt Transmission of Cardholder Data
iOS impact: All CHD over public networks uses TLS 1.2+ (PCI DSS 4.0 minimum; recommend 1.3). No early TLS or SSL. Fix: Your ATS config, certificate pinning, and ephemeral URLSession directly satisfy this. Document it in your compliance evidence package.
Req 6 — Develop and Maintain Secure Systems
iOS impact: Req 6.3 mandates addressing OWASP Mobile Top 10 (or equivalent). Req 6.4 requires addressing common vulnerabilities. Security review on every PR touching payment flows. SAST scanning (Xcode Analyze + commercial tools). Pen testing before major releases.
Req 8 — Identify and Authenticate Access
iOS impact: MFA for all access to CHD. Session tokens must expire. Force re-auth for high-value transactions. Fix: OTP + biometric for financial operations. Short-lived JWT (15 min). Step-up auth (transaction auth token) above a BDT threshold.
Req 10 — Log and Monitor — But Never Log CHD
iOS impact: Log must never contain card numbers, CVVs, PINs, or OTPs. A log file containing a PAN is itself in PCI scope. Fix: Custom scrubbing logger (see code below). Crashlytics configured to exclude sensitive views. Automated tests verify no CHD in log output.

                    withTemplate: rule.replacement)
            }
        }
        os_log("%{public}@", log: OSLog(subsystem: "com.fintech", category: category), safe)
    }

Tokenization vs Encryption — Payment Data Architecture

Hard

Tokenization replaces sensitive payment data (card number, wallet account) with a random, meaningless token. Encryption transforms data into ciphertext reversible with a key. For payment storage, tokenization wins: if the app is compromised, tokens are worthless without access to the token vault — a separate, hardened system your app never communicates with directly.

Why Tokenization Beats Encryption for Stored Payment Data

With encryption: if the app is compromised, the key may be extractable — attacker decrypts and gets real card numbers. With tokenization: attacker gets tok_8f3bKL9qR2pV. Without vault access it is permanently useless. The vault is a separate, isolated, PCI Level 1 certified system — breaking the mobile app gives zero access to it.

FinTech Tokenization Flow
Card Registration: User enters card in a PCI-validated SDK iframe (Stripe, Adyen etc.) — raw card data never reaches your code. SDK tokenizes card → returns payment_method_token. Your server stores the token linked to the user account.

Making a Payment: App sends { amount, payment_method_token, tx_signature }. Server validates SE-backed signature. Server calls payment gateway with token. Gateway dereferences token → processes payment. Real card number never transits your app or server.

OTP, TOTP & HOTP — From First Principles

Hard

TOTP (RFC 6238) generates a 6-digit code from a shared secret and the current Unix time window (default: 30s). Both client and server independently compute HMAC-SHA1(secret, floor(time/30)), then apply dynamic truncation to produce a 6-digit integer. No sync required — only clock synchronization matters (allow ±1 window for skew).

HOTP vs TOTP

  • HOTP (RFC 4226): Counter-based. Both sides share an incrementing counter. Risk: counter desync if codes are generated but not submitted.
  • TOTP (RFC 6238): Time-based. Counter = floor(unix_time / 30). Self-synchronizing via clock. Used by all modern MFA apps.
TOTP Algorithm — Step by Step
1. T = floor((current_unix_time − T0) / time_step)  →  e.g. floor(1700000000 / 30) = 56666666
2. Convert T to 8-byte big-endian
3. HMAC-SHA1(key=shared_secret, data=T_bytes) → 20 bytes
4. Dynamic truncation: offset = hmac[19] & 0xF; code = (hmac[offset..offset+4]) & 0x7FFFFFFF
5. OTP = code % 10⁶ → zero-pad to 6 digits
Swift — RFC 6238 TOTP Implementation
import CryptoKit

struct TOTPGenerator {
    let secret: Data
    let digits: Int          = 6
    let period: TimeInterval = 30

    func generate(at date: Date = .init()) -> String {
        hotp(counter: UInt64(floor(date.timeIntervalSince1970 / period)))
    }

    func validate(_ code: String, at date: Date = .init()) -> Bool {
        let t = UInt64(floor(date.timeIntervalSince1970 / period))
        return [t &- 1, t, t &+ 1].contains { hotp(counter: $0) == code }
    }

    private func hotp(counter: UInt64) -> String {
        var be = counter.bigEndian
        let msg = Data(bytes: &be, count: 8)
        let mac = Data(HMAC<Insecure.SHA1>.authenticationCode(
            for: msg, using: SymmetricKey(data: secret)))
        let offset  = Int(mac[mac.count - 1] & 0x0F)
        let binCode: UInt32 =
            (UInt32(mac[offset])     & 0x7F) << 24 |
            (UInt32(mac[offset + 1]) & 0xFF) << 16 |
            (UInt32(mac[offset + 2]) & 0xFF) << 8  |
            (UInt32(mac[offset + 3]) & 0xFF)
        let otp = binCode % UInt32(pow(10.0, Double(digits)))
        return String(format: "%0\(digits)d", otp)
    }
}

Transaction Signing & Non-Repudiation

Expert

Non-repudiation means a user cannot credibly deny having authorised a transaction. Without it you have "someone with the password did it." With it you have "the Secure Enclave on this specific device, confirmed by Face ID, signed this specific transaction at this specific timestamp — cryptographically provable." For disputes, fraud, and regulation this is the gold standard.

Architecture: Device Registration → Transaction Signing → Server Verification

During device registration: generate a P256 key pair in the Secure Enclave with .biometryCurrentSet access control. Upload the public key to FinTech servers tied to user + device. For each transaction above a threshold: construct a canonical byte string of all transaction fields, trigger Face ID (gates SE key access), sign inside the hardware, include DER-encoded ECDSA signature in the request. Server verifies using stored public key.

Canonical Representation — Why It's Critical

The signature is only as strong as what you sign. Use a deterministic, unambiguous canonical format. Store amounts as integer paisa (never floating point — 0.1 + 0.2 ≠ 0.3 in IEEE 754). Use pipe-separated fields in a fixed order. Server implements the identical canonical function.

Swift — Transaction Canonical + Secure Enclave Signing
struct TransactionPayload {
    let id:             UUID
    let senderWallet:   String
    let receiverWallet: String
    let amountPaisa:    Int64   // integer paisa — NEVER Double
    let timestampUnix:  Int64
    let nonce:          String  // server-issued single-use value
    let deviceId:       String

    /// Deterministic canonical bytes — server uses identical logic
    var canonical: Data {
        [id.uuidString.uppercased(), senderWallet, receiverWallet,
         String(amountPaisa), String(timestampUnix), nonce, deviceId]
            .joined(separator: "|")
            .data(using: .utf8)!
    }
}

Session Management & JWT Token Security

Hard

Session management is the mechanism that keeps a user "logged in" between requests without them re-entering credentials every time. In a payment app, getting this wrong is catastrophic — sessions that never expire leave users permanently exposed if their token is stolen; sessions that expire too aggressively frustrate users mid-transaction. The architecture must balance security, UX, and resilience.

JWT — Structure and Security Properties

A JSON Web Token (JWT) is a base64url-encoded string with three parts separated by dots: header.payload.signature. The header declares the algorithm (e.g., RS256). The payload contains claims (user ID, expiry, roles). The signature proves the token wasn't tampered with.

Critical: the iOS app should always verify the JWT signature if it makes any authorization decisions based on JWT claims. Never trust claims from an unverified token. For backend calls, the server always re-verifies — client-side verification is an extra safety layer.

Token Hierarchy for Payment Apps

Three-Token Architecture
1. Access Token (JWT) — Short-lived (15 minutes). Sent in every API request as Bearer token. Stored in memory only. Contains: user_id, wallet_id, device_id, roles, iat, exp. Signed RS256 or ES256.

2. Refresh Token — Long-lived (7–30 days). Opaque random string (not JWT). Stored in Keychain (WhenUnlockedThisDeviceOnly). Used only to obtain new access tokens. Single-use with rotation — each refresh invalidates the old token and issues a new one. If a compromised old token is replayed: server detects the anomaly, revokes the entire token family, forces re-login.

3. Transaction Authorization Token — Very short-lived (2 minutes). Issued after successful biometric challenge. Required for transactions above threshold (e.g., 500 BDT). This prevents a stolen session from being used to drain an account — attacker would need the user's biometrics too.

import Foundation
import CryptoKit

// ── Token models ─────────────────────────────────────────────────
struct AuthTokens: Decodable {
    let accessToken:  String
    let refreshToken: String
    let expiresIn:    TimeInterval  // seconds until access token expires
    let tokenFamily:  String        // for revocation tracking server-side
}

struct JWTPayload: Decodable {
    let sub:      String   // user ID
    let walletId: String
    let deviceId: String
    let exp:      Int64    // expiry unix timestamp
    let iat:      Int64    // issued-at unix timestamp
    let roles:    [String]
}

// ── Actor-isolated session manager ───────────────────────────────
actor SessionManager {

    static let shared = SessionManager()

    // Access token lives ONLY in memory — never written to disk
    private var accessToken:  String?
    private var tokenExpiry:  Date?
    private var cachedPayload: JWTPayload?

    // Serialises concurrent refresh attempts (no double-refresh race)
    private var refreshTask: Task<String, Error>?

    // ── GET VALID TOKEN ──────────────────────────────────
    func validAccessToken() async throws -> String {
        // Fast path: non-expired token in memory
        if let token = accessToken,
           let expiry = tokenExpiry,
           expiry > Date().addingTimeInterval(60) {  // 60s safety buffer
            return token
        }

        // Already refreshing? Join that task — don't launch a second one
        if let existing = refreshTask {
            return try await existing.value
        }

        // Start refresh
        let task = Task<String, Error> { [weak self] in
            guard let self else { throw SessionError.invalidated }

            // Load refresh token from Keychain
            let refreshToken = try KeychainService.load(key: .refreshToken)

            // Exchange for new tokens
            let newTokens = try await AuthAPI.refresh(token: refreshToken)

            // ROTATION: store new refresh token, old one is now invalid on server
            try KeychainService.save(newTokens.refreshToken, key: .refreshToken)

            // Cache access token in memory only
            await self.storeAccessToken(newTokens.accessToken,
                                           expiresIn: newTokens.expiresIn)
            return newTokens.accessToken
        }

        refreshTask = task

        do {
            let result = try await task.value
            refreshTask = nil
            return result
        } catch {
            refreshTask = nil
            // If refresh fails with 401, session is truly expired
            if case NetworkError.httpError(401, _) = error {
                await clearSession()
                throw SessionError.expired
            }
            throw error
        }
    }

    private func storeAccessToken(_ token: String, expiresIn: TimeInterval) {
        accessToken  = token
        tokenExpiry  = Date().addingTimeInterval(expiresIn)
        cachedPayload = decodeJWTPayload(token)
    }

    // ── LOGOUT ───────────────────────────────────────────
    func clearSession() {
        accessToken   = nil
        tokenExpiry   = nil
        cachedPayload = nil
        refreshTask   = nil
        // Wipe all session keys from Keychain
        KeychainService.wipeSessionData()
        // Notify UI to show login screen
        Task { await MainActor.run {
            NotificationCenter.default.post(name: .sessionExpired, object: nil)
        }}
    }

    // ── DECODE JWT PAYLOAD (no signature verification — server does that)
    // Client-side: used to read claims for UI (e.g. user name, wallet balance)
    private func decodeJWTPayload(_ jwt: String) -> JWTPayload? {
        let parts = jwt.split(separator: ".")
        guard parts.count == 3 else { return nil }

        // Base64url decode (JWT uses base64url, not standard base64)
        var base64 = String(parts[1])
            .replacingOccurrences(of: "-", with: "+")
            .replacingOccurrences(of: "_", with: "/")

        // Pad to multiple of 4
        let remainder = base64.count % 4
        if remainder > 0 { base64 += String(repeating: "=", count: 4 - remainder) }

        guard let data = Data(base64Encoded: base64) else { return nil }
        return try? JSONDecoder().decode(JWTPayload.self, from: data)
    }

    // ── AUTO-LOCK: Clear memory tokens when app backgrounds ──
    func handleAppBackground() {
        // Remove access token from memory — forces re-fetch (and possible re-auth)
        // when user returns. Refresh token in Keychain is still available,
        // so this is transparent for most users. For high-security mode,
        // also clear the refresh token and require full re-login.
        accessToken  = nil
        tokenExpiry  = nil
        cachedPayload = nil
    }
}

extension Notification.Name {
    static let sessionExpired = Notification.Name("com.fintech.sessionExpired")
}

    case expired, invalidated, biometricRequired
}

OWASP Mobile Top 10 — FinTech Mapped

Hard

The OWASP Mobile Top 10 is the industry-standard taxonomy of mobile security vulnerabilities. PCI DSS Requirement 6.3 requires addressing these. In an interview, walking through these with concrete FinTech-specific examples demonstrates that your security knowledge is applied, not theoretical.

M1 — Improper Credential Usage
What it is: Hardcoding API keys, secrets, or credentials in source code or config files. Using weak credentials. Storing credentials insecurely.

FinTech Example: A developer hardcodes the payment gateway API key in a Swift file. An attacker decompiles the app binary and extracts it using strings or Hopper Disassembler.

Fix: All secrets fetched at runtime from a secure config endpoint (encrypted, authenticated). No secrets in code or Info.plist. Rotate any key that was ever committed to git.
M2 — Inadequate Supply Chain Security
What it is: Third-party SDKs, libraries, or dependencies that introduce vulnerabilities or backdoors.

FinTech Example: An analytics SDK update silently adds code that reads the clipboard — clipboard may contain copied transaction IDs or OTPs.

Fix: Audit all third-party SDKs — check their privacy manifest (iOS 17+), review their requested entitlements, pin dependency versions in SPM/CocoaPods. Use Apple's PrivacyInfo.xcprivacy to declare and audit data access. Run SAST on entire dependency tree.
M3 — Insecure Authentication / Authorization
What it is: Weak login mechanisms, missing MFA, client-side authorization checks, accepting unsigned tokens.

FinTech Example: App checks user roles from JWT claims client-side to show/hide UI — but doesn't enforce these on the server. Attacker modifies the JWT payload (not the signature) and gets access to admin features because the server trusts client-provided role data.

Fix: ALL authorization decisions made server-side. Never trust client-provided role or permission data. Always verify JWT signature on the server. Short-lived tokens (15 min). MFA for all financial operations.
M4 — Insufficient Input / Output Validation
What it is: Not sanitizing or validating data before use — allows injection, XSS in WebViews, buffer overflows.

FinTech Example: Amount field accepts any string including negative numbers or decimals beyond 2 places. Attacker sends amount = -500 BDT causing a credit instead of debit on a vulnerable server implementation. Or: recipient field accepts phone numbers without length validation — API fuzzing reveals an error response that leaks internal stack traces.

Fix: Client-side validation for UX. Server-side validation for security (never trust client). Strict type enforcement — amounts are Int64 paisa only. Phone number format validation with regex. Never display raw server error messages to users.
M5 — Insecure Communication
What it is: Using HTTP, weak TLS versions, no certificate pinning, accepting self-signed certs.

FinTech Example: Corporate proxy with SSL inspection certificate is installed on a user's device (e.g., via MDM at their workplace). Without pinning, all transaction API calls are visible to the corporate proxy operator in plaintext.

Fix: HTTPS everywhere. TLS 1.3 minimum. Certificate pinning (SPKI hash). ATS hardened configuration. Ephemeral URLSession. All covered in Day 1 of this guide.
M6 — Inadequate Privacy Controls
What it is: Collecting more data than necessary, logging sensitive data, sending PII to analytics without consent.

FinTech Example: Crashlytics is configured with default settings — when the app crashes during a transaction, the crash report includes the full view hierarchy dump, which contains the transaction amount and recipient phone number rendered in UILabels.

Fix: Configure all crash/analytics SDKs to exclude sensitive views. Implement the scrubbing logger shown in the PCI section. Add accessibilityIdentifier to sensitive views and configure Crashlytics to mask them. Privacy manifest declares all data collection.
M7 — Insufficient Binary Protections
What it is: App binary can be reverse-engineered to extract sensitive logic, hardcoded strings, or algorithm details.

FinTech Example: Running strings FinTech.app/FinTech | grep -i key reveals the string "prod_api_key_v2_fintech_12345abcde". Or: Hopper Disassembler shows the jailbreak check function by name (isJailbroken), making it trivial for Frida to hook.

Fix: Compile-time string obfuscation for sensitive constants. Strip debug symbols in release builds. Function name obfuscation (iXGuard or similar). Enable all compiler hardening flags: SWIFT_OPTIMIZATION_LEVEL = -O, enable PIE, stack canaries, enable all Xcode security settings.
M8 — Security Misconfiguration
What it is: Debug builds shipped to production, unnecessary permissions, overly permissive ATS, debug logs left on.

FinTech Example: Build pipeline accidentally ships a Debug configuration build to the App Store. Debug build has NSAllowsArbitraryLoads=true in Info.plist for a developer's local test server, verbose logging enabled, and Frida gadget linked for testing — a fully exploitable app is live for users.

Fix: CI/CD pipeline enforces Release configuration for App Store builds. Separate Info.plist per configuration using xcconfig files. Pre-submit automated check that verifies ATS settings, logging level, and no debug frameworks are linked. Code signing enforcement.
M9 — Insecure Data Storage
What it is: Storing sensitive data in UserDefaults, unencrypted SQLite, log files, temp directories, or clipboard.

FinTech Example: Auth token stored in UserDefaults. On a jailbroken device, any app can read UserDefaults of another app (if sandbox is bypassed). Token extracted — attacker gains full account access without needing credentials.

Fix: Sensitive data → Keychain only (WhenUnlockedThisDeviceOnly). CoreData / SQLite → enable SQLCipher encryption or use Data Protection .complete. Clear clipboard after 30 seconds if app wrote to it. Never write sensitive data to temp files. Never log sensitive data.
M10 — Insufficient Cryptography
What it is: Using deprecated algorithms (MD5, SHA-1, DES, RC4), weak key sizes, rolling your own crypto, ECB mode, improper IV usage.

FinTech Example: Transaction IDs are generated using MD5 hash of timestamp + user ID. MD5 is collision-vulnerable — attacker could construct two transactions with the same ID, causing server-side confusion. Or: passwords are hashed with MD5 — a leaked database is cracked in hours with rainbow tables.

Fix: Use CryptoKit — it physically cannot use deprecated algorithms. SHA-256 minimum for hashing. AES-256-GCM for encryption. PBKDF2/Argon2 with 310,000+ rounds for password hashing. Unique random UUIDs for IDs — not hash-derived. Never implement custom crypto.

Networking & TLS

QWhat does ATS stand for and what does it enforce by default?

App Transport Security. By default: HTTPS only, TLS 1.2 minimum, forward secrecy required, SHA-256 minimum, no SHA-1 certs, 2048-bit RSA or 256-bit EC minimum.

QWhat is the difference between SecTrustEvaluate and SecTrustEvaluateWithError?

SecTrustEvaluate is deprecated (iOS 12). SecTrustEvaluateWithError is the modern replacement — it returns a Bool and populates a CFError with the failure reason. Always use the error variant; it gives you diagnostic info when a cert fails validation.

QCan you pin certificates in a WKWebView?

WKWebView has its own networking stack separate from URLSession. You can intercept via WKNavigationDelegate.webView(_:didReceive:completionHandler:) for authentication challenges — but it doesn't receive all TLS challenges reliably across iOS versions. For payment flows, avoid WKWebView entirely; use URLSession with your pinning delegate.

QWhat is OCSP and should you rely on it for certificate validation?

Online Certificate Status Protocol — a way to check if a certificate has been revoked by its CA. iOS checks OCSP by default in a "soft-fail" mode: if the OCSP server is unreachable, the connection is allowed anyway. This means OCSP provides limited revocation guarantees. Certificate pinning is a stronger guarantee because it doesn't depend on a third-party OCSP server being available.

QWhat is HTTP Strict Transport Security (HSTS) and how do you enable it for an iOS app?

HSTS is a server-side HTTP header (Strict-Transport-Security: max-age=31536000; includeSubDomains; preload) that tells browsers and HTTP clients to only use HTTPS for a domain, caching this policy for the specified duration. iOS URLSession respects HSTS headers. Enable it on your server. ATS enforces HTTPS at the app level, while HSTS provides a defence-in-depth layer by caching the policy in the OS HSTS store.

QWhat is a Man-in-the-Middle attack? Give the exact steps using Charles Proxy.

1. Attacker installs Charles Proxy CA certificate on victim's device (via profile installation or social engineering). 2. Device now trusts Charles as a CA. 3. Victim connects to api.fintech.com — Charles intercepts, presents its own cert signed by its (now-trusted) CA. Standard TLS validation passes. 4. Charles decrypts the traffic, logs it, re-encrypts it and forwards to the real server. Both ends think they have a direct connection. Certificate pinning defeats this because Charles's cert won't match the pinned SPKI hash.

QWhat is the Network framework and when would you use it instead of URLSession?

The Network framework (iOS 12+) is a lower-level API for custom TCP/UDP connections, local networking, and protocols beyond HTTP. Use it when you need: raw TCP/UDP sockets, custom application protocols, multipath TCP, local Bonjour networking, or finer-grained TLS control via NWProtocolTLS.Options. For standard REST APIs, URLSession is higher-level, more ergonomic, and handles HTTP semantics — prefer it.

Cryptography & Storage

QWhat is the difference between hashing, encryption, and encoding?

Encoding (Base64, URL encoding): reversible transformation with no secret — purely for representation, zero security. Hashing (SHA-256): one-way, deterministic, fixed output. Cannot be reversed. Used for integrity verification and password storage (with salt). Encryption (AES-GCM): reversible with the correct key. Provides confidentiality. Confusing these is a critical mistake — never "encode" a password or "hash" data you need to recover.

QWhat is a salt in password hashing and why is it necessary?

A salt is a random value concatenated with the password before hashing. Without salt, two users with the same password produce the same hash — an attacker who sees the hash database can use precomputed rainbow tables to crack millions of hashes at once. With a unique random salt per user, each hash is unique even for identical passwords, making precomputed attacks infeasible. The salt is stored alongside the hash (it doesn't need to be secret).

QWhat is the difference between kSecAttrAccessibleWhenUnlocked and kSecAttrAccessibleWhenUnlockedThisDeviceOnly?

The ThisDeviceOnly variant adds two restrictions: (1) the item is never synced to iCloud Keychain, and (2) the item cannot be migrated to another device via an encrypted backup restore. For sensitive auth tokens, always use ThisDeviceOnly — you don't want a user's session token to automatically appear on a new device, bypassing device registration checks.

QWhat is a timing attack and how does CryptoKit prevent it?

A timing attack exploits the fact that string comparison short-circuits — comparing "abc" with "axc" takes less time than comparing "abc" with "abx" because it stops at the first mismatch. An attacker can repeatedly submit guesses and measure response times to determine correct bytes one at a time. CryptoKit's HMAC.isValidAuthenticationCode uses constant-time comparison — it always takes the same time regardless of where a mismatch occurs, eliminating the timing signal.

QWhat happens if you reuse a nonce with AES-GCM?

AES-GCM becomes catastrophically insecure. If an attacker observes two ciphertexts encrypted with the same key and nonce, they can XOR them together to get the XOR of the plaintexts — recovering plaintext with no key needed. Additionally, the authentication key (derived from nonce + key in GCM) is exposed, meaning the attacker can forge authenticated ciphertexts. This is why CryptoKit generates a new random nonce automatically on each AES.GCM.Nonce() call — never construct nonces manually.

QWhat is key wrapping and when would you use it?

Key wrapping is encrypting a symmetric key with another key (the Key Encryption Key or KEK). Use it when you need to store an AES key securely — rather than storing it raw, you wrap it with a KEK that is itself stored in the Keychain or Secure Enclave. This creates a key hierarchy: compromise of the wrapped key file doesn't help without the KEK. Common pattern: generate a data encryption key (DEK) for encrypting large amounts of local data, wrap the DEK with a KEK stored in Keychain.

QWhat is the Secure Enclave's limitation on iOS that affects your crypto design?

The Secure Enclave only supports P-256 (NIST P-256 / secp256r1) keys — no RSA, no Ed25519, no other curves. This means: (1) If your server uses RSA for JWT signing verification, you can't use the SE for that. (2) For SE-backed operations you must use ECDSA P-256 for signing and ECDH P-256 for key agreement. Design your server-side key infrastructure around P-256 from the start if you want SE backing.

Payments, Architecture & Leadership

QWhat is a replay attack in the context of payment APIs?

An attacker captures a valid signed transaction request and re-submits it. Without protection, the payment executes twice. Prevention: (1) Server-issued nonces — the server generates a single-use random value, client includes it in the signed payload, server rejects any request with a previously used nonce. (2) Timestamp validation — server rejects requests older than ±5 minutes. (3) Idempotency keys — client includes a unique X-Request-ID; server deduplicates. All three layers together make replay practically impossible.

QWhat is rate limiting and how should a mobile app handle 429 responses?

Rate limiting caps the number of requests a client can make in a time window — protecting against brute force, scraping, and DoS. On receiving HTTP 429 Too Many Requests, check the Retry-After response header for the suggested wait time. Implement exponential backoff with jitter: wait min(base * 2^attempt, max_wait) + random_jitter. Never retry immediately on 429 — it makes rate limiting worse and may result in your IP being blocked. Show appropriate user feedback rather than spinning indefinitely.

QHow do you handle a transaction that succeeds on the server but the response never reaches the client (network timeout)?

This is the "uncertain transaction" problem. Solution: (1) Every transaction request includes a client-generated idempotency key (UUID). (2) On timeout, client retries with the SAME idempotency key. (3) Server checks if a transaction with that key was already processed — if yes, returns the original result (not a second transaction). (4) Client shows a "checking transaction status" UI and polls the transaction status endpoint until confirmed or definitively failed. Never show "failed" just because of a timeout — the money may have moved.

QWhat is SIM swapping and how does FinTech mitigate it at the app layer?

SIM swapping: attacker convinces a mobile carrier to transfer the victim's phone number to a SIM they control. They then receive the victim's SMS OTPs and gain account access. App-layer mitigations: (1) Device binding — register the device's Secure Enclave key; new device registration requires the old device to approve (or a manual review process). (2) Prefer in-app biometric confirmation over SMS OTP for transactions. (3) Anomaly detection — flag logins from new devices. (4) Allow users to view and remotely revoke trusted devices in app settings.

QWhat is the difference between UUID() and a cryptographically secure random value in Swift?

On Apple platforms, UUID() generates a version 4 UUID using the OS's CSPRNG — it IS cryptographically secure. However, UUIDs have a fixed format (8-4-4-4-12 hex) and 122 bits of entropy. For cryptographic purposes where you need arbitrary byte sequences (keys, nonces, tokens), use var bytes = [UInt8](repeating: 0, count: 32); SecRandomCopyBytes(kSecRandomDefault, bytes.count, &bytes) or CryptoKit's SymmetricKey(size: .bits256) which uses the same CSPRNG. Never use arc4random for security-critical randomness — it's fine for game logic, not cryptography.

QHow would you implement a "secure overlay" that prevents the app switcher from showing sensitive screens?

Register for UIApplication.willResignActiveNotification. In the handler, add a full-screen blur view or branded splash screen over the window. Remove it in UIApplication.didBecomeActiveNotification. This ensures the app switcher captures only the overlay, not the transaction screen. Additionally use UIScreen.capturedDidChangeNotification to detect screen recording and hide sensitive content in real-time. For text fields, set isSecureTextEntry = true — this also prevents the OS from caching the text in the screenshot database.

QA junior developer on your team pushes code that stores the OTP secret in UserDefaults. How do you handle this as Lead?

Three parallel tracks: (1) Immediately: flag it in code review with a clear explanation of why it's wrong — UserDefaults is unencrypted, not protected by Keychain access controls, and included in unencrypted backups. Reject the PR. (2) Fix: pair with the developer to move it to Keychain with proper accessibility class. Review their understanding before approving. (3) Systemic: this reveals a gap — add a security code review checklist, add a SAST rule that flags UserDefaults writes containing the words "secret", "token", "key", "otp". Consider a brief team session on iOS secure storage. Don't shame — educate.

QWhat is the Bangladesh Bank's position on mobile financial service security and how does it affect your technical decisions?

Bangladesh Bank's Payment Systems Department has issued guidelines for Mobile Financial Services (MFS) including: mandatory 2-factor authentication for all transactions, strong encryption for data in transit (TLS), secure storage of customer data, and audit trail requirements. As Lead iOS engineer, these guidelines directly mandate: MFA implementation (OTP + biometric), TLS enforcement (ATS + pinning), encrypted storage (Keychain + Data Protection), and transaction logging (security event telemetry without logging PII). Non-compliance risks regulatory action against the operator licence. Always frame your security decisions in terms of both technical best practice AND regulatory compliance — in a fintech interview, this demonstrates business awareness.
